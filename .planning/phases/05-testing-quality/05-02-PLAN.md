  <action>
    Create .github/workflows/ci.yml with the following configuration. Per the agent's discretion on trigger strategy, use both push and pull_request triggers (push to main, pull_request targeting main).

    Workflow name: "CI"

    Triggers:
    - push: branches [main]
    - pull_request: branches [main]

    Jobs — single job named "test" running on ubuntu-latest:

    Step 1: Checkout — actions/checkout@v4

    Step 2: Setup Go — actions/setup-go@v5 with:
      - go-version: '1.25' (match go.mod)
      - cache: true (enables automatic Go module caching)

    Step 3: go mod tidy check — run `go mod tidy` followed by `git diff --exit-code go.mod go.sum`. If the diff is non-empty, fail the job (ensures go.mod/go.sum are always tidy). This catches dependency drift early.

    Step 4: go vet — run `go vet ./...`. Fail on any vet warnings.

    Step 5: golangci-lint — uses golangci/golangci-lint-action@v6 with:
      - version: latest
      - args: --timeout=5m ./...
      - skip-cache: false
      If this step fails (e.g., golangci-lint-action v6 not available), the job should continue but report the failure as a warning, not block CI. Use `continue-on-error: true` on this step so lint failures don't block merging.

    Step 6: Test with race detector — run `go test -race -count=1 ./...`. Do NOT use `-v` flag to keep output manageable. Fail on test failures.

    Step 7: Coverage profile — run `go test -coverprofile=coverage.out -covermode=atomic ./...` to generate coverage data.

    Step 8: Display coverage — run `go tool cover -func=coverage.out` to print per-function coverage to the CI log (not stored, just displayed).

    Step 9: Upload coverage artifact — actions/upload-artifact@v4 with:
      - name: coverage
      - path: coverage.out
      This makes the coverage profile downloadable as a CI artifact for local inspection.

    Do NOT add any secrets or environment variable configuration — the CI runs unit and integration tests that use httptest mocking (no real credentials needed).
  </action>

    Targets to add (all .PHONY):
    - test: Run `$(GO) test -race -count=1 ./...`. Add echo header "◆ Running tests..."
    - coverage: Run `$(GO) test -coverprofile=coverage.out -covermode=atomic ./...` followed by `$(GO) tool cover -html=coverage.out -o coverage.html` and echo "◆ Coverage report: coverage.html". This generates an HTML report for local browsing.
    - vet: Run `$(GO) vet ./...` with echo "◆ Running go vet..."
    - lint: Run `golangci-lint run ./... --timeout=5m` with echo "◆ Running golangci-lint...". The target should gracefully handle missing golangci-lint (check with `command -v golangci-lint` and print a clear install message instead of failing cryptically).
    - ci: A meta-target that runs vet → test → lint in sequence. Each step prints a clear header. Use `&&` chaining so failure in any step stops the pipeline. Echo "◆ CI pipeline complete" at the end.

    **Create .golangci.yml at project root:**

    Per the agent's discretion and the research findings, configure golangci-lint with:
    - run.timeout: 5m
    - run.go: '1.25'
    - linters: enable the following (disable defaults not explicitly listed):
      - govet (built-in, catches common bugs)
      - staticcheck (comprehensive Go static analysis)
      - ineffassign (detect ineffectual assignments)
      - unused (detect unused code)
      - errorlint (find error wrapping issues — relevant for Phase 1's error return patterns)
      - gosimple (simplify code, aligns with Go idioms)
    - linters-settings:
      - staticcheck: checks: ["all", "-ST1000"] (all checks except "incorrect comment for exported" — the project uses unexported functions extensively)
      - errorlint: check type and comparison on errors
    - issues:
      - max-issues-per-linter: 0 (no limit)
      - max-same-issues: 0 (no limit)
      - exclude-use-default: false (start clean without default exclusions)

    This configuration matches the project's current code patterns while catching real issues. If golangci-lint reports pre-existing issues on the first run, they should be noted but are not blocking (the `ci` CI target in Makefile continues-on-error is already set, and the GitHub Actions step uses continue-on-error: true).
